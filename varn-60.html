Värn-60

Timing tests for post-quantum key exchange — with controls that say what the test can see
Sabrina Hackfort · Independent Researcher · ORCID 0009-0007-7458-2487
❦ ❦ ❦

A cipher can be broken not only by its mathematics but by its timing. If an implementation takes a few nanoseconds longer on some secret inputs than on others, that difference can give the secret away, one step at a time. VÄRN-60 — codename Anu — measures whether the decapsulation step of ML-KEM (FIPS 203), the new standard for post-quantum key exchange, takes a different time for different ciphertexts.

What it does

VÄRN-60 gives one key several ciphertexts — one that is accepted and several that must be rejected — and times the decapsulation of each, round after round, in a fresh random order. A sign test counts which of two inputs was the slower one in each round, and a finding only counts if a second run confirms it. Five libraries are measured with the same procedure in the same run: PQClean, RustCrypto ml-kem, liboqs, AWS-LC and libcrux.

Measuring a finished program is treacherous. A careless measurement finds leaks that are not there, or misses real ones. So every run carries its own controls. Two identical inputs must show no difference; if they do, the run cannot be used. And one input is slowed down on purpose by a small added piece of work; if the run cannot see that delay, it says so instead of reporting a pass. From the delay it did see, the run states how small a difference it could have found.

What It Found

Two machines were measured on 25 November 2026: an Apple M4 Pro and a shared cloud server. On neither were identical inputs told apart: none of the 226 comparisons of identical inputs raised a false alarm. The M4 detected an added delay of about two nanoseconds in every attempt, the cloud server one of about ten. Between an accepted ciphertext and a rejected one — a ciphertext for another key, or the same ciphertext with a single bit flipped — no library showed a difference on either machine. Where a run was too noisy to see its own control delay, the tool said so instead of reporting a pass.

One thing did turn up. On the M4, a ciphertext consisting only of zero bytes was decapsulated about one nanosecond faster than a valid one, in each of seven runs, at the edge of what a single run can detect. When the processor's data-independent-timing mode was switched on, the difference was no longer detected. Such a ciphertext is public, so nothing secret leaks here. But it indicates that on this processor the running time of this code depends on the data it computes with unless that mode is set.

The numbers, and the files they come from, are in the repository.

What It Does Not Claim

“No difference found” is not a proof that an implementation runs in constant time. It holds for the inputs that were tried, on the machine that was used, down to the size the controls show. Each input class is a single fixed ciphertext, and leaks of the KyberSlash kind — a division whose time depends on a secret — are not yet tested systematically. Power, electromagnetic and cache side channels are outside its scope.

Corrections

Earlier versions of this page said more than the tool could show. Three statements are withdrawn:

  • that ML-KEM-768 “is constant-time” in five implementations. A timing test cannot show that.
  • that the tool was the first of its kind. dudect, tlsfuzzer (which also has an early toolkit for ML-KEM), RTLF, ctgrind and TIMECOP came before it, and VÄRN-60 builds on their ideas.
  • that Kyber decapsulation leaked (stated from March 2026, withdrawn in October 2026). The difference came from measuring one class after another on a machine that drifts; it disappeared when the classes were measured in alternation.

Earlier versions also described measurements of ML-DSA and SLH-DSA, hardware performance counters and a licensed audit. None of that is part of the tool today. Version 2.0.0 does one thing, is free software under the Apache License 2.0, and anyone can run its measurements.
